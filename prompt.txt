Start Phase 3G — Spending Velocity Detection.

FIRST STEP ONLY: build the deterministic backend/API. Do NOT build frontend yet. Do NOT use Gemini.

Goal:
Detect when the user's recent spending pace is unusually high compared with their historical spending pace.

Add an authenticated endpoint such as:

GET /api/analytics/spending-velocity?window_days=3

Return:

* current_window_spend
* baseline_window_spend
* velocity_ratio
* percentage_change
* window_days
* baseline_method
* alert_level
* start_date
* end_date

Rules:

* Analyze expense/debit transactions only.
* Never count income/credits as spending.
* Use Decimal for monetary calculations.
* User isolation via authenticated user.
* Current window = most recent N days.
* Build a deterministic historical baseline from comparable historical periods.
* Clearly document the baseline methodology.
* Require sufficient historical data before producing a strong alert.
* Do not generate an alert solely because the user spent a large absolute amount.
* The alert should be based on spending pace relative to the user's own history.

Avoid:

* Gemini
* arbitrary hardcoded "3x = bad" logic without documenting it
* future-date transactions
* double counting split transactions
* changing existing transaction data

For split transactions:

* total spending must remain the original transaction amount.
* Do not count split rows as separate expenses.

Tests:

* elevated spending
* very high spending
* insufficient history
* zero historical baseline
* income/credit exclusion
* date boundaries
* Decimal precision
* split transaction no-double-counting
* user isolation
* authentication
* invalid window_days
* future transactions excluded
