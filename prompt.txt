Start Phase 3E — Split Transactions.

FIRST STEP ONLY: implement the backend data model and API. Do NOT build the frontend yet.

Requirements:

Allow one transaction to be divided into multiple category splits.

Example:
Transaction = ₹5,000

* Groceries = ₹3,000
* Shopping = ₹1,500
* Household = ₹500

Rules:

* Split amounts must sum EXACTLY to the original transaction amount.
* Use Decimal for all money calculations.
* A split must belong to the same authenticated user's transaction.
* Prevent negative/zero split amounts.
* Prevent duplicate/invalid category references where applicable.
* A transaction without splits must continue working exactly as before.
* Existing transaction APIs must not break.

Add:

* database model/schema + migration
* Pydantic models
* authenticated create/update/delete/list split endpoints
* service-layer validation
* user isolation
* transaction total validation

Important:

* Existing transaction amount remains authoritative.
* Do not change the transaction amount when splitting.
* Category analytics should NOT be changed yet unless required by the model.
* Do NOT add frontend UI.
* Do NOT add Gemini.
* Do NOT modify unrelated features.

Tests:

* create valid split
* exact total matching
* under/over total rejection
* zero/negative amounts
* update splits
* delete splits
* user isolation
* unauthenticated access
* transaction without splits still works
* Decimal precision
* rollback/atomicity on failed split operations

Run the full backend + frontend test suites.
